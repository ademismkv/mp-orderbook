## 2026-08-12 — Market Data Feed: the pipeline's last stage, closed with the real transport already built

Added the final piece of ROADMAP.md's pipeline: `Order Books -> Risk -> Execution Reports -> Market Data Feed`. Execution Reports (day 18) are private — Ack/Reject/Fill back to the one participant who submitted an order. Market data is public — a normalized view of every book-affecting event, for anyone subscribed. `mdfeed::MDEvent` (Add/Cancel/Delete/Trade/Replace, 50-byte fixed wire record) is deliberately not literal ITCH bytes — that would just be re-deriving itch_messages.h. What matters more here is that this feed travels over the *actual* transport day 14/15 already built and verified against real sockets: MoldUDP64 framing (sequence numbers, gap detection, request/retransmission) over real UDP multicast, not a simulated callback pretending to be a feed.

`Sequencer::on_message()` gained a fifth optional parameter, `MarketDataCallback`, defaulting to empty so it's still the one class used by every earlier test. It only fires for something that actually happened to a book — a risk-rejected or arena-rejected order produces a Reject execution report but never a market data event, since nothing observable changed for a subscriber to see.

One real correctness issue caught before it ever ran: my first draft published an Add event with the order's full *submitted* quantity, not what actually ended up resting. If an incoming order immediately crosses on arrival (this engine's own `match()` can still do that, even against real historical "already resting" ITCH data — see day 17), part or all of its quantity fills instantly and never touches the book. Real ITCH's own convention is that Add Order describes what's actually on the book, not what was submitted — this repo already established that reading on the *inbound* side (day 17: "Add Order messages are, by construction, the resting remainder after matching"). Fixed by computing `resting_qty = submitted_qty - filled_qty` from the trades `match()` itself produced, and publishing the Add event with that instead. If resting_qty is 0, no Add event is published at all — nothing rested, only the Trade event(s) for what did happen. Same fix applied to Order Replace, with a fallback to a plain Delete when a replacement order fully crosses and never rests, since the old order still needs to disappear from anyone tracking it even if nothing new appears.

Verification is the actual point of this stage, not just "it compiles": ran the full real 691,421-message file through Sequencer with Risk enabled, capturing 445,131 market data events (every accepted add/cancel/delete/executed/replace), and snapshotted the true final best-bid/best-ask for all 828 symbol shards directly from the real `OrderBookV2` objects. Then — in a separate thread with no access to that internal state — encoded and published those events as real MoldUDP64 downstream packets over a real UDP multicast socket (loopback, same `IP_MULTICAST_IF`-to-127.0.0.1 workaround as day 15), deliberately dropping 5 packets outright to force real gap detection and a real unicast retransmission round-trip. A third thread, a subscriber, joined the multicast group, decoded the wire bytes, and reconstructed a shadow order book purely from the public feed — no shortcuts into the Sequencer's own state.

First run exposed two real problems, not simulated ones. First: sending ~2,226 packets back-to-back overran this sandbox's default loopback UDP receive buffer before the single-threaded subscriber could drain it — 7,200 of 445,131 events delivered, 1,847 gap requests, a real packet-loss storm from real socket behavior. Fixed by pacing the sender (1ms between packets) and requesting a larger `SO_RCVBUF` (asked for 8MB, kernel granted ~416KB — logged both numbers rather than assuming the request succeeded). Second: the test's own stop condition was wrong — it stopped as soon as `session.ended()` went true, but MoldUDP64's end-of-session packet carries the *next expected* sequence number and can trigger a gap request for data that hasn't finished retransmitting yet; stopping on `ended()` alone raced real in-flight recovery and misreported it as loss. Fixed by making the actual stop condition "every event delivered" (`delivered_count == total_events`), with `ended()` tracked and printed only as information. On one run the end-of-session packet itself was lost over real UDP and never arrived at all — logged honestly as "no (lost over real UDP)" rather than treated as a failure, since it's a control message carrying no data of its own; completeness is what `delivered_count` actually measures.

After both fixes: 445,131/445,131 events delivered on every one of 3 consecutive runs, 5-7 real gap-recovery round trips per run (the 5 deliberate drops plus, honestly, 0-2 additional real loopback losses under load — not filtered out or explained away), and 0/828 symbol mismatches between the shadow book built from nothing but the wire feed and the true engine state. That last number is the real claim of this stage: a subscriber that only ever sees the public market data wire bytes can reconstruct every symbol's best bid and ask exactly, with no privileged access to the matching engine's internals.

This closes ROADMAP.md's full pipeline vision — Feed Handler (day 13-16) -> Sequencer (day 17) -> Risk (day 18) -> Execution Reports (day 18) -> Market Data Feed (day 19) -> real UDP multicast subscriber, all running against real Nasdaq ITCH 5.0 data end to end, not five components that each pass their own isolated tests.

Still open: order types beyond Limit (Market, IOC, FOK, Post-Only), position-based risk limits, and the full measurement-methodology list (pinned cores, TSC calibration, `perf`, flamegraphs) — none of that touched yet.
