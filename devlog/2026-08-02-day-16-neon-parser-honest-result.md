## 2026-08-02 — NEON batch parser: correct, not measurably faster

Roadmap originally said "AVX2 parser." Checked the target hardware first: this repo's real numbers all come from Apple Silicon, and this dev sandbox is ARM64 too — AVX2 is x86-only and can't run on either. Built NEON instead (see previous entry for that correction) — a batch decoder for Add Order messages (26.6% of real traffic, the dominant type), byte-swapping `order_ref_number` 2-at-a-time via `vrev64q_u8` and `shares`/`price` 4-at-a-time via `vrev32q_u8`.

Correctness: differentially checked against the scalar decoder on every real 'A' message in the sample — 183,724 of them, 0 mismatches, every run.

Performance: went looking for a speedup number and the first one I got (1.33x) turned out to be measuring the wrong thing. `parse_message()` returns a `std::variant` sized for the largest of 23 message types (72 bytes) even when decoding a 48-byte message — comparing NEON against that was comparing against variant-construction overhead, not decode cost. Added `decode_add_order_scalar()` as a direct, fair baseline (same struct in, same struct out, only the byte-swap strategy differs) and reran: 5 runs, speedup ranged 0.58x–1.51x, straddling 1.0x with no consistent direction.

Checked the actual generated assembly instead of guessing why. At `-O3`, GCC already compiles the scalar `shares`/`price` (32-bit) and `stock_locate`/`tracking_number` (16-bit) field reads down to single `rev`/`rev16` instructions — the "slow shift-loop" NEON was supposed to beat doesn't exist for those fields. The one field where scalar is genuinely worse is `order_ref_number` (8 bytes, unaligned offset — compiler falls back to a chain of 8 byte-loads-and-shifts instead of one `rev`), which is exactly where NEON's `vrev64q_u8` should win — but that narrow, real advantage gets absorbed by the batch's gather overhead (4 `memcpy` calls to assemble each lane array) and doesn't show up as a net wall-clock win at this message size.

Not rounding this up to a speedup claim. The honest result: verified correct against real data, performance neutral-to-noisy on real measurement, root cause understood rather than shrugged at. If this needs to actually be faster, the next lever isn't more SIMD — it's processing larger contiguous batches (this test used one 20MB slice's worth of 'A' messages) or restructuring to avoid the gather/scatter round-trip, and either would need to be measured again before claiming anything.
