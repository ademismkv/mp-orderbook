## 2026-08-12 — Sequencer built, Feed wired to Order Books, a real engine bug found doing it

Built the missing middle of ROADMAP.md's `Feed -> Sequencer -> Order Books` pipeline. The real problem a Sequencer has to solve: after Add Order, ITCH messages don't carry the stock symbol — Cancel/Delete/Executed/Replace only carry an order_ref_number, and the spec says outright that firms must retain the side/symbol from the original Add Order. `Sequencer` tracks that mapping and translates every message type into this engine's existing `add()`/`cancel()`/`reduce()` calls, routed to a per-symbol `OrderBookV2` shard — same interpretation `replay_lobster.cpp` already established and verified against real data: Add Order lets this engine's own `match()` decide what crosses; Order Executed is applied as a `reduce()` against the resting order's quantity, not re-matched, because the real exchange already decided that fill happened.

First real run against the full 691,421-message sample crashed: `std::bad_alloc`, trying to allocate ~13GB. Rebuilt under AddressSanitizer to get a real stack trace instead of guessing, and traced it to `ensure_index_for_price()` — a real order in the real data, symbol `TVIX`, price `888888800` (a $88,888.88 sentinel/garbage value, not a real quote), asked the level array to grow by ~891 million entries. Nothing in `OrderBookV2` before this point validated that a caller-supplied price was sane — a single malformed or sentinel-valued order could OOM a whole shard, independent of anything upstream.

Fixed it in the engine itself, not just the Sequencer: added `kMaxLevels`, a hard ceiling (16.7M levels, ~268MB worst case) on `ensure_index_for_price()`'s growth/rebase paths, throwing a catchable `std::runtime_error` instead of attempting the allocation. This is exactly the kind of guard a real pre-trade risk stage (price bands, still open on ROADMAP.md) should also catch upstream — but the book itself shouldn't be one bad price away from OOM regardless of what sits in front of it. Re-verified against the full existing test suite before trusting it: 10/10 unit tests, differential fuzz including the rebase-walk generator that exercises this exact code path (8 seeds, all matching v1), TSan-checked threaded test — all still pass, the guard is a no-op for every legitimate existing workload.

End-to-end result on the real file: 691,421 messages, 0 parse failures, 828 symbols sharded, 0 unrouted references, 0 book invariant violations, 38 orders caught by the new guard (mostly likely more sentinel-price garbage like TVIX's). One thing worth being straight about: `trades_produced` came out 0 on this real slice. Checked before assuming it was a bug — it isn't. ITCH's Add Order messages are, by construction, the resting remainder after the real exchange already matched anything that crossed on arrival; replaying just that stream rarely reproduces a fresh cross on its own, especially across 828 thin symbols in an early, reference-data-heavy slice rather than one liquid symbol's full session (contrast `replay_lobster.cpp`: 13,298 trades from a full AAPL day). To actually prove the wiring can produce a trade when one should happen, added two synthetic but realistically-shaped crossing orders fed through the exact same `Sequencer::on_message()` path — confirmed a real trade comes out the other end.

This closes the "biggest missing technical component" gap from the original roadmap review: Feed and Order Books were two things that worked in isolation and had never been connected. Now they are, and finding a real OOM bug by actually wiring real data through — instead of stopping at "the parser passes its own tests" — is exactly why that step mattered.

Still open: Risk, Execution Reports, and Market Data Feed (the rest of the pipeline), plus the measurement methodology work (pinned cores, TSC calibration, etc.) — none of that is touched yet.
