## 2026-08-12 — CI hardening: zero-alloc gate, sanitizer jobs, real benchmark regression detection

Closed the CI/testing gaps from ROADMAP.md: benchmark-per-commit, p99 regression detection, a zero-allocation assertion, and sanitizer builds in the matrix.

**Zero-allocation assertion** (`cpp/tests/test_zero_alloc.cpp`) overrides the global `operator new`/`delete` for one executable and counts calls across 200,000 steady-state add/cancel/reduce/cross operations on a pre-warmed `OrderBookV2`. This is what "the arena design means no malloc on the hot path" — a claim README.md already makes — actually looks like checked instead of assumed. It found a real gap immediately: `free_list_` (the arena's list of freed node slots) had no upfront `reserve()`, unlike `index_` right next to it which already did, with a comment explaining exactly why. The first several `cancel()`s after construction were each a real heap growth. Fixed with `free_list_.reserve(arena_capacity)` — free_list_ can never hold more than arena_capacity entries, so this is a hard, correct bound, not a guess. Verified the test actually catches the regression it claims to (reverted the fix locally, reran, got a real `FAIL: ... (1 allocation, 8 bytes)`) before trusting it.

**Sanitizer builds** are now two separate CI jobs (ASan+UBSan can't combine with TSan — both intercept malloc): `sanitizers-asan-ubsan` builds and runs `test_order_book_v2`, 5 differential fuzz seeds, and the real NASDAQ replay, all under `-fsanitize=address,undefined`; `sanitizers-tsan` runs the existing threaded pipeline test under `-fsanitize=thread`, promoting a command that was previously only documented in README's "Build & test" section as something to run by hand into something that actually runs on every push.

**Benchmark regression detection** is a new script, `cpp/bench/check_regression.py`, gating `bench_v2`'s throughput and p99 against a committed baseline (`cpp/bench/baseline.json`). The previous CI comment said "informational only — CI runners are noisy, not a perf gate" — true, but that also meant nothing would ever actually notice a regression landing. Measured 5 consecutive `bench_v2` runs on this repo's own dev sandbox before picking thresholds: throughput swung 6.34-7.79M ops/sec and p99 swung 209-250ns from noise alone, on hardware this repo controls directly — a shared GitHub Actions runner will be noisier still. Set the gate at a 45%-throughput-drop / 2.5x-p99 threshold: wide enough to survive that measured noise without crying wolf, tight enough to still catch an actual multi-x regression (the class of bug — a reintroduced allocation, a dropped `-march=native`/LTO flag, an accidental O(n) path — this is actually meant to catch). `p50` and `p999` are reported but deliberately not gated: at 42-83ns absolute values, a single nanosecond of scheduler jitter is a huge percentage swing, not a signal. Verified all three paths of the script directly: a normal run passes, a synthetic bad run (1.5M ops/sec, 900ns p99) correctly fails with a clear report, and `--update-baseline` correctly rewrites the baseline file (restored afterward — this flag is for a human to run deliberately and review in a diff, never something CI calls itself, or a real regression could get silently absorbed into a new "normal" one noisy run at a time). Every commit's raw `bench_v2` output is also uploaded as a CI artifact, giving the "benchmark every commit" a historical record beyond just pass/fail.

**Full pipeline coverage made explicit in CI**, not just implied: the existing `ctest` step in `ci.yml` already ran every test this repo has via CMakeLists.txt's `add_test(...)` entries — including `itch_parser_real_data`, `moldudp64_session`, `udp_multicast_e2e`, `sequencer_wiring`, and `market_data_feed` — but the CI YAML gave no indication any of that was happening beyond one generic step name. Relabeled and commented it explicitly, so what CI actually verifies on every push — the full Feed → Sequencer → Risk → Order Books → Execution Reports → Market Data Feed pipeline against real Nasdaq data, not just the core engine — is visible in the CI file itself, not something you'd only discover by reading CMakeLists.txt.

Re-verified the whole thing didn't regress anything already established: full differential fuzz (8 seeds, still MATCH), `test_order_book_v2` (10/10), and a full `quickstart.sh` run end to end — all pass, `zero_alloc` now included in that report (0 allocations, PASS).
