## 2026-08-12 — Risk engine and Execution Reports wired into the Sequencer

Added the next two stages of ROADMAP.md's pipeline: `Sequencer -> Order Books -> Risk -> Execution Reports`. `RiskEngine::check()` runs before an order ever reaches `OrderBookV2::add()`, not after — a real exchange rejects a bad order at the gate, it doesn't let the book find out the hard way. Three checks: fat-finger (qty over a configurable ceiling), price bounds (absolute sanity range) and price bands (percentage deviation from a reference price — last real trade if there's trade history for the symbol, else the book's own current best bid/ask/mid, since a symbol's very first order has no reference to judge against). A fourth check, self-trade prevention, is scoped honestly to what the feed actually supports: real ITCH's Add Order — No MPID Attribution, 183,724 of 183,767 real Add Orders in the sample, carries no participant identity at all. Only Add Order — MPID Attribution does. Self-trade checking only runs where an identity exists to check — not faked for the anonymous majority.

Execution Reports (`Ack`/`Reject`/`Fill`) are emitted through the exact same `Sequencer::on_message()` path that processes the order, not a bolt-on reporting layer that could drift out of sync with what the book actually did. Both `RiskEngine*` and the report callback are optional parameters, defaulting to off, so this is still the one `Sequencer` used by day 17's wiring test, not a second implementation.

Hit a real GCC quirk building `RiskEngine`: a default argument `Config cfg = {}` for a nested aggregate-with-default-member-initializers, referenced from inside the enclosing class body, fails to compile — "default member initializer... required before the end of its enclosing class." Reproduced standalone in `/tmp/repro.cpp` before touching the real code, confirmed it wasn't a project-specific mistake, fixed with out-of-line delegating constructors defined in the `.cpp` file where the class is already complete.

Also caught my own bug before it ever compiled: my first draft of the `OrderExecuted` branch fed the message's nanosecond timestamp into `risk->on_trade()` as if it were a price. Plain Order Executed carries no price field — only the resting order's original price applies, and this message doesn't repeat it. Order Executed With Price does carry a real execution price and feeds the reference correctly; plain Order Executed doesn't touch the price-band reference at all.

Verification against the full real 691,421-message file, with Risk and report capture both enabled: 0 parse failures, 828 symbols sharded, 0 book invariant violations, 204,889 execution reports emitted (202,351 acks, 2,538 rejects, 0 fills — same "no organic crosses in this slice" result as day 17, for the same reason). Added an accounting check rather than trusting the totals on faith: ack count matches successful add_orders + replaces exactly, reject count matches add_rejected + risk_rejected exactly, fill count matches trades_produced exactly.

One number worth being straight about: all 2,538 real-data rejections were price-band violations — 0 fat-finger, 0 out-of-bounds, 0 self-trade. Checked before assuming the risk engine was just being noisy: the default 25% band is a demonstration value, not a tuned one, and this slice is 828 mostly-thin symbols early in a session, where a book's best-bid/best-ask spread can legitimately be wide before real liquidity shows up — exactly the condition where a naive percentage band flags real, valid quotes. That's a real, honest finding about tuning a risk engine against real market microstructure, not a bug in the mechanism itself; the mechanism is separately proven correct below.

Real data alone didn't happen to exercise every rule (no self-trades or fat-fingers occurred naturally in this slice), so added targeted synthetic cases through the same `on_message()` path: an oversized order gets rejected with `max_order_size` in the reason string; a price 5x away from an established ~$9.90-$10.00 reference gets rejected as a price-band violation; the same MPID (`ACME`) resting on both sides of a symbol gets its crossing order rejected for self-trade; and — the check that actually proves #3 isn't just "reject all crosses on that symbol" — a *different* MPID (`XYZZ`) crossing the exact same book trades normally. Also confirmed Risk doesn't accidentally block a legitimate cross: two ordinary opposing orders on a synthetic symbol still produce a real trade with Risk fully enabled. All checks pass, re-verified identically in both the scratchpad and `second_brain/mp-orderbook`, plus a clean rerun of the existing `test_order_book_v2` unit suite (10/10) to confirm nothing in the untouched engine core regressed.
